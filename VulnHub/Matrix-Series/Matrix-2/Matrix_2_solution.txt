[11] VULNERABILITIES IDENTIFIED
================================================================================

1. UNAUTHENTICATED LOCAL FILE INCLUSION — file_view.php (Critical)
   Detail   : file_view.php on port 12322 passes the user-supplied `file`
              parameter directly to a file-reading function with no
              authentication, path sanitisation, or allowlist check.
   Impact   : Arbitrary file disclosure; reads /etc/passwd, nginx config,
              and .htpasswd. In more complex scenarios, LFI can chain into
              RCE via log poisoning or /proc/self/environ injection.
   Fix      : Validate and restrict the file parameter to an explicit
              allowlist; move sensitive files outside the web root; require
              authentication on all service endpoints.

2. SENSITIVE CREDENTIAL FILE READABLE VIA LFI (High)
   Detail   : The nginx virtual host for port 1337 stored its .htpasswd
              file at /var/www/p4ss/.htpasswd — inside the web server's
              readable path — allowing LFI to extract it directly.
   Impact   : Hashed credentials exposed; cracked in under one second.
   Fix      : Store credential files outside the web root; remediate the
              LFI vulnerability; enforce strong, unique passwords.

3. WEAK PASSWORD — APACHE MD5 HASH (High)
   Detail   : The password for Tr1n17y was "admin" — present near the top
              of the rockyou wordlist. The $apr1$ hash format is also
              computationally weak by modern standards.
   Impact   : Cracked instantly by John the Ripper.
   Fix      : Enforce strong password policy; consider bcrypt or Argon2
              for password hashing; disable HTTP Basic Auth in favour of
              token-based authentication.

4. CREDENTIALS HIDDEN VIA STEGANOGRAPHY (High)
   Detail   : The system password for n30 (P4$$w0rd) was concealed inside
              h1dd3n.jpg using Steghide, served from an authenticated but
              otherwise unprotected HTTP endpoint.
   Impact   : Any attacker who obtained Trinity's credentials could
              retrieve and extract the image to escalate further.
   Fix      : Never store credentials in steganographic or encoded form
              on the server. Obfuscation is not encryption.

5. SUID BINARY WITH ARBITRARY CODE EXECUTION — morpheus (Critical)
   Detail   : /usr/bin/morpheus is a SUID root binary with awk-like
              behaviour. Passing 'BEGIN {system("/bin/sh")}' spawns a root
              shell — identical to the GTFOBins technique for awk.
   Impact   : Any user with execute permission on morpheus gains an
              immediate, unrestricted root shell.
   Fix      : Remove SUID bit: chmod u-s /usr/bin/morpheus
              Audit all SUID binaries: find / -perm -4000 -type f 2>/dev/null
              Never set SUID on interpreter-style or shell-spawning binaries.

================================================================================
[12] SECURITY RECOMMENDATIONS
================================================================================

1. Web Application Security
   - Validate and allowlist all user-supplied file paths; never pass raw
     input to file-reading functions
   - Require authentication on every service endpoint regardless of content
   - Store configuration files and credential stores outside the web root
   - Conduct regular web application penetration tests and code reviews

2. Credential & Secrets Management
   - Enforce strong, randomly generated passwords on all accounts
   - Use modern hashing algorithms (bcrypt, Argon2) instead of $apr1$ MD5
   - Never store credentials — even encoded or steganographically concealed —
     on the server
   - Use a dedicated secrets manager (e.g. HashiCorp Vault) for sensitive
     material

3. SUID Binary Hardening
   - Regularly audit SUID/SGID binaries:
       find / -perm -4000 -o -perm -2000 -type f 2>/dev/null
   - Remove SUID from any binary capable of executing arbitrary commands
   - Prefer Linux capabilities (setcap) over SUID where possible
   - Check all custom and third-party binaries against GTFOBins before
     deployment: https://gtfobins.github.io/

4. Network & Service Hardening
   - Restrict access to high-numbered service ports via firewall rules or VPN
   - Enable fail2ban or equivalent on all externally reachable services
   - Centralise logging (nginx access/error, auth events, shell activity)
     and alert on anomalous patterns
